# Bounded Delivery Sessions

## Persisted contract

After task planning, the orchestrator records **every known unfinished task exactly once** in `pipeline.batches` as stable `BATCH-XX` entries. Include all future batches as `pending`; keep `current_batch` pointing to the active or blocked batch. Each batch records `state` (`pending`, `running`, `closing`, `completed`, `blocked`), `close_reason`, `task_ids`, `depends_on` (batch IDs), `context_estimate` (principal tokens and assumptions), `handoff_path`, `principal_session_id` (when available), and `closeout` checkpoints. Existing completed task IDs remain in `pipeline.tasks` with their evidence and commits; do not reassign or replay them. If a task is split, update task artifacts, batch assignments and dependencies atomically before dispatch; never duplicate the original ID. A batch is an accepted bounded **session scope**, not a claim that the product pipeline or its deferred runtime checks completed. Blocked batches retain their task assignment; only explicit replan after verifying partial output may move unfinished IDs. Do not mark the full pipeline completed until every task's complete QA **and** runtime acceptance is evidenced.

Batch order is a suggested safe session order, not a fabricated dependency. Honor only actual `depends_on` and task dependencies, plus file ownership/overlap constraints. Replan remaining pending batches if scope changes; retain completed/blocked evidence. One safely reviewed task can be a complete batch. Never start a later batch in the same principal session after closure, even if capacity remains.

## Slice work before implementation

1. Inventory every approved, unfinished task and its deliverable boundary, owner, acceptance/validation evidence, real prerequisites, candidate files and overlap strategy. Separate independent domain slices (for example, API contract and UI consuming an already-defined contract); do not invent dependencies to impose a batch order. Keep each slice independently reviewable, with explicit out-of-scope work. Split a task too large for one safe session **before dispatch**, giving the new scopes distinct IDs and updating artifacts/dependencies/assignments together; preserve the original task's history without assigning its ID twice.
2. For each slice, estimate **principal** intake as dispatch/context passed to agents + condensed returns + QA and likely correction/retry exchanges + commit/state handoffs; identify closeout separately within the configured `dispatchReserve` (do not double-count it). Label size and uncertainty (small/medium/large; low/medium/high), state assumptions and evidence for estimates; these are planning estimates, not measured telemetry. Do not sum full child-agent transcripts. Use actual current principal observation when available; if unavailable/stale, use the existing unknown-stop-new-work policy rather than a fabricated measurement.
3. Pack independent slices into a proposed session scope only if **measured current intake + estimated additional principal cost of all proposed work + configured `dispatchReserve` < configured `stopNewWork`**. Include context already spent on startup, design, planning, retries and this transcript: neither compaction nor a new batch resets consumption. Recheck the gate at each dispatch and before QA; estimated future sessions start with a conservative fresh-session assumption, then require their own measurement on resume. Never size a batch by a fixed task count or wall-clock hours. Several small independent tasks may share a batch and run in parallel when the combined dispatch/report cost fits; a single oversized task must be split or deferred.
4. Propose stable `BATCH-XX` scopes for **all** remaining tasks, including future `pending` batches, not just the first wave. Record per-task cost components, size/uncertainty, dependencies and shared-file merge strategy in task artifacts/index; record each batch's sum, baseline assumption and reserve in the proposal and `context_estimate` narrative. Distinguish parallel execution waves **within** a session batch from session boundaries. If planning itself uses the safe room, follow the [planning-only checkpoint](#planning-only-checkpoint-before-a-batch-starts); do not dispatch implementation or invent a completed task batch merely to close that session.

### Planning-only checkpoint before a batch starts

When planning exhausts safe room before implementation starts, stop new dispatch and write a durable `.opencode/plan/<context>/references/planning-session-handoff.md` (or a stable per-session suffixed path for multiple planning sessions), independent of the two retained session files. Record approved **and unapproved** design/planning/task artifacts and their approval status, the inventory of all known unfinished tasks, all known future `pending` batches and their dependencies (or explicitly what remains to be planned), principal budget observation or `unknown`, session identity, branch/dirty state, outstanding decisions and the exact next action. Persist the handoff path, planning stage and resumable STOP checklist as narrative in existing `pipeline.handoff.additional_context` and `resume.next_action`; use existing history for checkpoint updates. Do not introduce required YAML fields, invent a completed task batch or set `current_batch` when none exists; existing pending batch assignments stay pending.

Close the planning session in order: refresh `project-structure.md`, `docs-catalog.md` and `INDEX.md` (or record checked-no-change); write the **preliminary** planning handoff and pointer; run `learning-improvement` → `continuous-learning` (wait for approval/decline before applying changes) → `session-save` once; finalize the handoff with session file, Git/doc state and exact next action; reconcile any authorized remaining non-task docs/state commit after the chain and verify handoff, state and checkpoint read-back. If approval or authorization is pending, persist that exact pending checkpoint and question; do not skip ahead or claim readiness. On `/delivery-pipeline:resume`, load the pointer and reconcile evidence and session identity first, then execute only missing closeout stages in order, including pending user approval; do not repeat approved planning or completed skills. After verified closure, require a **fresh** confirmed principal session and safe budget before any implementation dispatch. The same principal session may finish missing closeout only, not start implementation after closure.

## Principal context budget (guidance, not a hard limit)

Use `.opencode/context-budget.json` as the single source for `target`, `stopNewWork`, `closeBy`, `absoluteContextReference` and `dispatchReserve`. Begin planning closeout at `target`, stop new work at `stopNewWork`, and complete closeout by `closeBy`. `absoluteContextReference` is a user-selected model context reference, **not** a measured model capacity or a server-enforced limit. Estimate principal intake, condensed agent reports, QA/retry/commit handoffs, and closeout; do **not** sum full child-agent histories. Allocate the configured `dispatchReserve` for closeout. Split oversized independent work before implementation with explicit scope, ownership, file boundaries and task-ID updates. Prefer smaller batches; never fill the quota just to use it.

**The closeout reserve is protected, not spare implementation capacity.** Budget enough room for the mandatory `learning-improvement` → `continuous-learning` → `session-save` chain, including any approval exchange, plus documentation refresh, durable handoff, final state and authorized commit/read-back. These steps must run at every applicable closeout, including budget-stopped or blocked started batches and planning-only sessions; they are not optional or deferred until the entire product is complete. If estimated closeout exceeds `dispatchReserve`, stop earlier or reduce scope rather than consuming its room on another dispatch. Persist interrupted or approval-pending checkpoints and resume only missing stages; never mark closeout complete or ready for a new session without the chain.

After restart, `read-context-budget` in `.opencode/tools/read-context-budget.ts` may be available. The companion `.opencode/plugins/context-budget.plugin.ts` registers the host's project-scoped SDK client (including its authentication/in-process transport); `.opencode/lib/context-budget-client.ts` keeps it scoped to directory and worktree. The tool file exports only the OpenCode tool; tests live in `.opencode/tests/`. **Invoke it from the principal session**, never from a child agent: tool context supplies the caller's session ID/directory but cannot determine whether that caller is principal. It calls the SDK's `session.messages` for that session and directory with `query.limit: 20`. An optional uncredentialed loopback-only `serverUrl` explicitly overrides the host client; only when plugin registration is absent does the legacy fallback try `http://localhost:4096`. The TUI may have no listener there or use a random port: an unreachable fallback is `unknown`, not a reason to assume a server is running. The 5-second timeout bounds **asynchronous waiting**; it cannot interrupt synchronous JSON parsing and does not guarantee a response-byte or memory limit. No usable completed assistant observation in the returned window, a failed message, or zero tokens yields `unknown`, not a safe dispatch. It reports a usable latest **completed assistant** input snapshot as `tokens.input + tokens.cache.read + tokens.cache.write` with timestamp, model, message and caller session IDs. This sum is a conservative approximation and **may double-count for some providers**; it is neither cumulative billing nor universally exact provider accounting and cannot enforce a hard cap. Observations older than 120 seconds or in the future return `unknown`. In-flight output may lag; compaction is not a reset. Tool/plugin changes are not exposed to already-running sessions until OpenCode restarts. If a restarted principal still gets `unknown`, inspect its sanitized reason and verify tool/plugin discovery and session access; do not treat standalone tests as live evidence or configure a server solely for this feature.

Read the budget before dispatch, after agent returns and before QA. For a new implementation dispatch require a measured current observation **plus estimated additional principal dispatch/report cost plus `dispatchReserve` < `stopNewWork`**. At or above `stopNewWork` stop new dispatch; at or above `closeBy` close promptly using reserved room. Unknown telemetry, invalid/missing configuration, unavailable server, missing tool, stale observation or inability to estimate cost => **unknown-stop-new-work**: finish only safe checkpoints, write handoff, close or block; never invent token counts. QA/review of already active work only when safe; preserve partial without false approval when not. Record measurements or `unknown`, reason and estimate in handoff. A blocked environment is not an invitation to use the next batch in the same session.

**Per-dispatch authorization gate:** A policy result of `continue` is necessary but never sufficient to dispatch. Before **each** new implementation or QA agent dispatch (or independent parallel group), require a recent measured principal snapshot + estimated **additional** principal intake for the proposed dispatch, report, likely corrections, QA and commits not already reflected in that snapshot + configured `dispatchReserve` **strictly < configured `stopNewWork`**. The snapshot is the latest completed assistant input, **not** a live counter: obtain a fresh reading when possible and include principal activity since `observedAt`, including in-flight output, in the additional estimate; never treat unobserved output as free. Preserve the unknown/stale stop and configured `stopNewWork` / `closeBy` rules above.

### Carryover on an early stop

On `budget` or `unknown-stop-new-work`, reconcile the current batch before closing: list completed IDs with actual QA/commit/runtime evidence and list each unfinished ID, including unstarted and partially active work. For each unfinished ID, archive the original assignment and reason in history/handoff, then move it **exactly once** to a stable new `pending` batch (or an existing eligible pending batch) with real dependencies and file-overlap constraints updated. Record `moved_to: BATCH-XX` as narrative/handoff metadata, not a new mandatory YAML schema field; persist removal from the old assignment and addition to the destination together, and verify each unfinished ID occurs once across batches. Keep existing completed batch IDs and SHAs stable; never renumber completed batches. For an active partial task, carry exact artifacts, validation/QA status, attempts, ownership and next action; do not mark it completed or redo accepted work. The old batch may close as a scope checkpoint only after no unfinished IDs are orphaned; a budget stop does not turn deferred runtime acceptance into a pass. A `blocked` batch retains its assignment unless an explicit, evidence-checked replan moves unfinished IDs. No carryover batch may dispatch in the closing principal session.

## Closeout state machine (resume each missing checkpoint only)

1. Set current batch `closing` with reason (`budget`, `scope-finished`, `blocked`, `interrupted`; record `unknown-stop-new-work` as the budget reason when applicable) and stop new dispatch. Finish safe active review or record partial artifacts, errors and attempt counts; never infer QA/validation from file existence. For an early budget/unknown stop, apply [carryover](#carryover-on-an-early-stop) before finalizing the batch.
2. Reconcile authorized per-task implementation/docs commits and SHAs using [task commit rules](execution-phases.md#task-commit). If approval or authorization is pending, record pending commit rather than replaying it. Retain deferred runtime statuses even after code-QA commits.
3. Refresh `project-structure.md`, `docs-catalog.md`, `INDEX.md` based on actual file changes; record each as updated or checked-no-change. Save a **preliminary durable handoff** at `[BATCH_HANDOFF_FILE]` before STOP. Include the fields in [batch handoff template](../../../template/batch-handoff-template.md). Sessions retained by `save-session` (two files) are NOT the handoff store.
4. Run `learning-improvement` → `continuous-learning` → `session-save` once per batch. Respect continuous-learning's user approval gate. If awaiting approval, persist `closing` and `next_action: ask user for approval`; never skip the gate or pretend the chain finished. STOP does not recursively trigger another STOP. Record each checkpoint immediately; on resume run **only missing** stages.
5. After session-save, finalize handoff with session file, git/dirty state, documentation review and next action; persist final state and make only authorized remaining **non-task** docs/state commit after the chain, following commit convention. Reconcile resulting SHA, verify handoff/pipeline and checkpoint artifacts can be read, then set `ready_for_new_session: true` and `completed` (scope accepted) or `blocked` (unresolved dependency). If a final commit is not authorized or fails, record it as pending, remain `closing`, and ask for resolution; never claim ready. A blocked batch can be safely handed off only with its blocker explicit and authorized closeout complete.
6. Tell user to start a **new** OpenCode session and run `/delivery-pipeline:resume` only after verification. Never run clear/reset or manage OS processes for them. Do not start a pending later batch in the closing principal session.

## Resume and legacy recovery

Resolve variables, load pipeline and its `handoff_path`, then inspect branch/HEAD, tracked and untracked/staged changes, commit SHAs and last-edit validation relevance. Compare the persisted principal session ID with the current one when available. Do not derive fresh-session status merely from invocation of the resume command. Reconcile partial commits and artifacts idempotently; files/build outputs alone never prove checks, QA or completed steps. Do not re-commit SHAs already recorded or overwrite unrelated user changes. Hydrate targeted task files and relevant design/architecture paths from the handoff, not full transcripts or all planning docs. If state conflicts, record uncertainty and stop new dispatch until reconciled.

If the **current batch is still `running`** after an ordinary interruption, resume that **same** batch (including in the same principal session) only after evidence, attempts, dependencies, file ownership and budget are reconciled. In a fresh session, confirm identity as below and measure that session's budget; partial work stays partial until checked. If the batch is `closing`, resume **only missing closeout checkpoints** in either session; if `completed` or `blocked` after closeout, the same principal session cannot advance to a later batch. If IDs are unavailable, require the user's explicit confirmation of a fresh session **before advancing**; confirmation does not bypass budget or reconciliation. Once a fresh session is confirmed, dependencies and blockers are satisfied, and previous closeout verified, advance `current_batch` to the next pending eligible batch; otherwise report the blocked next action. Carryover tasks in a pending batch are future work, even if they started in the closing session.

For legacy pipelines, preserve every original task status, commit, blocker and history entry. Assign only unfinished task IDs to new batches; keep code-QA approval distinct from deferred runtime acceptance. Never count old task-index execution waves as new sessions or re-run completed implementation.

An initially migrated `blocked` batch with pending closeout checkpoints is a **pre-execution blocker record**, not a claim that a previous batch session closed. In a confirmed fresh session, if its prerequisite becomes available, reconcile evidence and reactivate that **same** batch as `running`; do not force a fake historical STOP chain before its first execution. If still blocked, persist the current blocker and handoff, and close the attempted session via the normal checkpoints only when a real session batch was started. A previously `closing` batch must finish its missing closeout before any new dispatch.
