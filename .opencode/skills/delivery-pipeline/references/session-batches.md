# Bounded Delivery Sessions

## Persisted contract

After task planning, the orchestrator records **every known unfinished task exactly once** in `pipeline.batches` as stable `BATCH-XX` entries. Include all future batches as `pending`; keep `current_batch` pointing to the active or blocked batch. Each batch records `state` (`pending`, `running`, `closing`, `completed`, `blocked`), `close_reason`, `task_ids`, `depends_on` (batch IDs), `context_estimate` (principal tokens and assumptions), `handoff_path`, `principal_session_id` (when available), and `closeout` checkpoints. Existing completed task IDs remain in `pipeline.tasks` with their evidence and commits; do not reassign or replay them. If a task is split, update task artifacts, batch assignments and dependencies atomically before dispatch; never duplicate the original ID. A batch is an accepted bounded **session scope**, not a claim that the product pipeline or its deferred runtime checks completed. Blocked batches retain their task assignment; only explicit replan after verifying partial output may move unfinished IDs. Do not mark the full pipeline completed until every task's complete QA **and** runtime acceptance is evidenced.

Batch order is a suggested safe session order, not a fabricated dependency. Honor only actual `depends_on` and task dependencies, plus file ownership/overlap constraints. Replan remaining pending batches if scope changes; retain completed/blocked evidence. One safely reviewed task can be a complete batch. Never start a later batch in the same principal session after closure, even if capacity remains.

## Principal context budget (guidance, not a hard limit)

Plan for **140,000–180,000** principal-context tokens, referencing **200,000** only as an absolute model context reference. Estimate principal intake, condensed agent reports, QA/retry/commit handoffs, and closeout; do **not** sum full child-agent histories. Allocate a 20,000-token closeout reserve. Split oversized independent work before implementation with explicit scope, ownership, file boundaries and task-ID updates. Prefer smaller batches; never fill the quota just to use it.

After restart, `read-context-budget` in `.opencode/tools/read-context-budget.ts` may be available. Its logic lives in `.opencode/lib/context-budget.ts` with tests in `.opencode/tests/read-context-budget.test.ts`; the tool file exports only the OpenCode tool. **Invoke it from the principal session**, never from a child agent: tool context supplies the caller's session ID/directory but cannot determine whether that caller is principal. It calls the OpenCode SDK's `session.messages` for that session and directory with `query.limit: 20` recent messages (optional loopback-only `serverUrl`, default `http://localhost:4096`). The 5-second timeout bounds **asynchronous waiting**; it cannot interrupt synchronous JSON parsing and does not guarantee a response-byte or memory limit. No usable completed assistant observation in the returned window, a failed message, or zero tokens yields `unknown`, not a safe dispatch. It reports a usable latest **completed assistant** input snapshot as `tokens.input + tokens.cache.read + tokens.cache.write` with timestamp, model, message and caller session IDs. This sum is a conservative approximation and **may double-count for some providers**; it is neither cumulative billing nor universally exact provider accounting and cannot enforce a hard cap. Observations older than 120 seconds or in the future return `unknown`. In-flight output may lag; compaction is not a reset. The tool is not exposed to already-running sessions until OpenCode restarts. Do not assume a new API or configure a server solely for this feature.

Read the budget before dispatch, after agent returns and before QA. For a new implementation dispatch require a measured current observation **plus estimated principal dispatch/report cost plus 20,000 reserve < 160,000**. At >=160,000 stop new dispatch; at >=180,000 close promptly using reserved room. Unknown telemetry, unavailable server, missing tool, stale observation or inability to estimate cost => **unknown-stop-new-work**: finish only safe checkpoints, write handoff, close or block; never invent token counts. QA/review of already active work only when safe; preserve partial without false approval when not. Record measurements or `unknown`, reason and estimate in handoff. A blocked environment is not an invitation to use the next batch in the same session.

## Closeout state machine (resume each missing checkpoint only)

1. Set current batch `closing` with reason (`budget`, `scope-finished`, `blocked`, `interrupted`) and stop new dispatch. Finish safe active review or record partial artifacts, errors and attempt counts; never infer QA/validation from file existence.
2. Reconcile authorized per-task implementation/docs commits and SHAs using [task commit rules](execution-phases.md#task-commit). If approval or authorization is pending, record pending commit rather than replaying it. Retain deferred runtime statuses even after code-QA commits.
3. Refresh `project-structure.md`, `docs-catalog.md`, `INDEX.md` based on actual file changes; record each as updated or checked-no-change. Save a **preliminary durable handoff** at `[BATCH_HANDOFF_FILE]` before STOP. Include the fields in [batch handoff template](../../../template/batch-handoff-template.md). Sessions retained by `save-session` (two files) are NOT the handoff store.
4. Run `learning-improvement` → `continuous-learning` → `session-save` once per batch. Respect continuous-learning's user approval gate. If awaiting approval, persist `closing` and `next_action: ask user for approval`; never skip the gate or pretend the chain finished. STOP does not recursively trigger another STOP. Record each checkpoint immediately; on resume run **only missing** stages.
5. After session-save, finalize handoff with session file, git/dirty state, documentation review and next action; persist final state and make only authorized remaining **non-task** docs/state commit after the chain, following commit convention. Reconcile resulting SHA, verify handoff/pipeline and checkpoint artifacts can be read, then set `ready_for_new_session: true` and `completed` (scope accepted) or `blocked` (unresolved dependency). If a final commit is not authorized or fails, record it as pending, remain `closing`, and ask for resolution; never claim ready. A blocked batch can be safely handed off only with its blocker explicit and authorized closeout complete.
6. Tell user to start a **new** OpenCode session and run `/delivery-pipeline:resume` only after verification. Never run clear/reset or manage OS processes for them. Do not start a pending later batch in the closing principal session.

## Resume and legacy recovery

Resolve variables, load pipeline and its `handoff_path`, then inspect branch/HEAD, tracked and untracked/staged changes, commit SHAs and last-edit validation relevance. Compare the persisted principal session ID with the current one when available. Same principal session: resume missing closeout only; refuse advancing batches. If IDs unavailable, require the user's explicit confirmation of a fresh session before advancing. Do not derive fresh-session status merely from invocation of the resume command. Reconcile partial commits and artifacts idempotently; files/build outputs alone never prove checks, QA or completed steps. Do not re-commit SHAs already recorded or overwrite unrelated user changes. Hydrate targeted task files and relevant design/architecture paths from the handoff, not full transcripts or all planning docs. If state conflicts, record uncertainty and stop new dispatch until reconciled. Once a fresh session is confirmed, dependencies and blockers are satisfied, and the previous closeout verified, advance `current_batch` to the next pending eligible batch; otherwise report the blocked next action.

For legacy pipelines, preserve every original task status, commit, blocker and history entry. Assign only unfinished task IDs to new batches; keep code-QA approval distinct from deferred runtime acceptance. Never count old task-index execution waves as new sessions or re-run completed implementation.

An initially migrated `blocked` batch with pending closeout checkpoints is a **pre-execution blocker record**, not a claim that a previous batch session closed. In a confirmed fresh session, if its prerequisite becomes available, reconcile evidence and reactivate that **same** batch as `running`; do not force a fake historical STOP chain before its first execution. If still blocked, persist the current blocker and handoff, and close the attempted session via the normal checkpoints only when a real session batch was started. A previously `closing` batch must finish its missing closeout before any new dispatch.
